# flight-bot

Telegram-бот подписки на статус авиарейсов. На вход — номер рейса, спрашивает
дату, дальше шлёт все изменения (задержка, смена терминала/выхода, вылет,
прилёт, отмена) до завершения рейса.

## Данные (РФ): бесплатно, платное — план B

По РФ глобальные ADS-B-трекеры (FR24/OpenSky/FlightAware) над страной рваные —
основа не они, а **расписательно-статусные данные аэропортов**.

| Источник | Статус | Как |
|---|---|---|
| **SVO** (Шереметьево) | ✅ готов | JSON табло `svo.su/timetable/?search=<no>&direction=<dir>` (до 10.2026 — `www.svo.aero/bitrix/timetable/`, теперь 301), ключ не нужен; редиректы проходим |
| **DME** (Домодедово) | ✅ готов | поиск по номеру `www.dme.ru/book/live-board/?searchText=…&direction=D\|A` + `Detailed?id=`. Даёт план/факт, статус, тип ВС, зону вылета (терминала не даёт — бот ставит его по зоне: E — Т2, международные; A, C, D, F — Т1) и из бегущей строки статуса — стойки, время регистрации, выход, начало посадки, новое время при задержке (если колонка факта пуста — со страницы рейса или из бегущей строки: «23:50 Вылет задерживается»); **не даёт** IATA (только город) и ленты. С зарубежного адреса сервера бота хост не отвечает → транспорт уходит в **scrape.do** (`geoCode=ru`) |
| **LED** (Пулково) | ✅ готов | **JSON-API** `pulkovoairport.ru/api/?type=departure\|arrival&when=-1\|0\|1&search=<цифры>` — самый полный источник: план/оценка/факт, стойки и окно регистрации, выход, посадка (план/факт), терминал, IATA и город, промежуточная точка, кодшер, лента багажа на прилёте. `search` — подстрока по цифрам, код авиакомпании сверяем сами. С сервера бота доступен напрямую |
| **VKO** (Внуково) | ✅ готов | HTTP API `/rest/flights/online`: известный JS-челлендж вычисляется без Chromium, cookies сохраняются отдельно для прямого соединения и RU-прокси. Ответ API декодируется по публичной конфигурации страницы. План/оценка/факт обоих плеч с часовыми поясами, регистрация, терминал, выход, кодшеры, лента багажа. При ошибке — резервный Playwright (`RENDER_URL`), затем AirLabs. |
| **DXB** (Дубай) | ✅ готов | статический JSON всего аэропорта `dubaiairports.ae/docs/passengerslibraries/flights-library/flights-data.json`, без ключа: вылеты и прилёты на вчера/сегодня/завтра, терминал, выход, лента, план/оценка/факт (вылет — взлёт, прилёт — on-block), кодшеры. Времена с «Z», но это местное +04:00. Файл 3,7 МБ кэшируется на 60 с. Стоек и посадки нет |
| **BAH** (Бахрейн) | ✅ готов | `POST bahrainairport.bh/api/FlightProxy/departures\|arrivals` `{"date":"дд/мм/гггг"}`, без токена: сегодня/завтра, план/оценка/факт (+03:00), выход, зона стоек, лента. «Факт» позже текущего момента (API так отдаёт завтрашние рейсы) не принимаем |
| CPT (Кейптаун) | ❌ | у ACSA только SharePoint-форма поиска (на EK770 сама отвечает таймаутом), публичного JSON нет — CPT покрывает AirLabs |
| Прочие РФ (антибот/JS) | ⏳ | тот же `Fetcher`: напрямую, при блоке — scrape.do |
| **AirLabs** (airlabs.co) | ✅ готов | резолвер «номер→аэропорт» и статус вне наших табло (им же пользуется Flighty). Проверено с сервера: знает и SU2128 (времена сходятся с табло до минуты), и внутренний S7 2050 DME→Сочи. Городов не отдаёт, плиток стоек/выхода нет — фолбэк |
| **AeroDataBox** (RapidAPI) | ✅ готов | **расписание по номеру на сегодня +5 дней**, по всему миру: `/flights/number/<no>/<с>/<по>`. Табло держат только вчера/сегодня/завтра — даты дальше берём отсюда. Дорого: запрос = 6 единиц из 400 бесплатных в месяц, поэтому только при поиске (кэш 6 ч, ошибка — 10 мин, не больше 1000 номеров; одновременные поиски одного номера — один запрос), в опрос не ходит. Бюджет — `AERODATABOX_BUDGET` (60) платных попыток, включая неудачные, за скользящие 31 день, счётчик в SQLite; сверх — даты только с табло, без сообщения пользователю. Ключ `AERODATABOX_API_KEY` |

Flighty (flighty-mcp) в расчёт не берём: он читает локальную базу macOS-приложения,
на сервере это не источник.

## Архитектура

Плагинная, бизнес-логика не знает происхождения данных:

- `FlightSource` — источник статуса по номеру+дате → `list[FlightSnapshot]`
  (реализовано: SVO, DME, LED, VKO, AirLabs).
- `airports` — справочник IATA ↔ русский город: везде показываем «код +
  название» (`KZN Казань`), чего не дало табло — дополняем.
- `AirportResolver` — «номер рейса → аэропорт(ы)» (`FlightRoute`), чтобы понять,
  чьё табло опрашивать. Для Москвы роль резолвера играет опрос настроенных
  табло (они сами по номеру отдают маршрут); для остального мира — AirLabs,
  даты вперёд — AeroDataBox.
- `FlightSnapshot` — нормализованный снимок; diff двух снимков = список изменений.
- `http.Fetcher` — один транспорт для табло, три ступени: **напрямую → свой
  RU-прокси → scrape.do**. Свой прокси — SSH-туннель с SOCKS до хоста с российским адресом
  (`RU_PROXY_URL`, юнит `deploy/ru-proxy.service`; на RU-хосте ничего не
  ставится, прокси делает sshd), scrape.do (`geoCode=ru`) — платный резерв.
  Провал ступени запоминается на процесс, чтобы не платить таймаутом каждый
  опрос; последняя ступень пробуется всегда. TLS проверяется по certifi плюс
  `flight_bot/certs/*.pem` — промежуточные сертификаты, которые табло не
  отдают в цепочке (Пулково с 12.10.2026).
- Поиск опрашивает табло параллельно (табло дольше 15 с для поиска — пусто),
  AirLabs — только если табло пусты, одним запросом (направление ему не важно). Ответ источника на (рейс, дата,
  направление) общий на 60 с для поиска и всех подписок, одновременные
  запросы склеиваются: 10 подписок на один рейс — один запрос за цикл. Факт: часть табло не отвечает
  с зарубежного адреса сервера бота, с российского — отвечает.
- `VkoClient` — HTTP-клиент Внуково: напрямую → `RU_PROXY_URL`, затем
  источник использует `Renderer` при ошибке. Известный `get_jhash` переведён
  на Python, произвольный JS не исполняется. Повторная проверка обновляет cookies;
  неизвестный алгоритм и повреждённые ответы уходят в резерв. Кэш поиска по
  номеру+направлению — `RENDER_CACHE_SEC` (75 с), одновременные запросы используют
  его совместно. Пагинация ограничена; прямой путь после сбоя пробуется через 5 минут.
  Пустой корректный ответ API не запускает Chromium. Времена `gates_st/et`
  не выдаются за подтверждённые факты посадки.
- Подписка хранит **источник**, где рейс нашли, и опрашивается им первым;
  остальные — только если он рейс потерял. Иначе с ростом числа табло каждый
  опрос ходил бы по всем подряд.

## Другие аэропорты: РФ и не-РФ

- **РФ.** Единого API нет, у каждого аэропорта своё табло, универсального
  HTML-парсера не бывает. Модель — **по плагину на аэропорт**, добавляемому по
  потребности: класс `FlightSource` (~100 строк) + боевая фикстура + тест,
  одна строка в `registry.SOURCES`. Москва и Петербург закрыты; дальше по
  спросу. Гео-блок — `Fetcher` (RU-прокси / scrape.do), для VKO — `VkoClient` (HTTP + cookies), при неизвестном челлендже —
  рендер-сервис (`Renderer`).
- **Не-РФ.** Свои парсеры не пишем: универсальный слой — **AirLabs**
  (маршрут, статус, гейт/терминал); даты на 5 дней вперёд — **AeroDataBox**.
- Каскад всегда *табло → AirLabs → (AeroDataBox)*: AirLabs не всеведущ
  (GF013 он не знает), табло — первоисточник.

```
номер рейса ──> AirportResolver ──> аэропорт(ы) ──> FlightSource(табло) ──> FlightSnapshot
                                                                              │
                              подписка ── опрос по расписанию ── diff ────────┘──> пуш в Telegram
```

## Мониторинг источников

Табло ломаются тихо (Пулково с 12.10.2026 — TLS). `health.py` считает ошибки
каждого источника подряд: 6 ошибок и не меньше 30 минут с первой — владельцам
из `OWNER_IDS` в личку приходит «⚠️ Источник … не отвечает с … МСК», после
первого успешного ответа — «✅ снова отвечает». Ошибка — исключение источника;
«рейса нет» — успех. Серия и факт тревоги хранятся в SQLite (`source_health`):
выкатка посреди сбоя не обнуляет счёт и не теряет «✅».
Ошибка в теле ответа AirLabs (`{"error": …}` — истёк ключ, исчерпан лимит) —
тоже ошибка, а не «рейса нет» (кроме `not_found` — это и есть «рейса нет»); ошибки IATA-обогащения через AirLabs учитываются
так же. `AIRLABS_KEY_EXPIRES` (ГГГГ-ММ-ДД) — за 7 дней до даты и после неё
владельцам раз в день приходит «⏳ Ключ AirLabs истекает …» / «⚠️ … истёк».

## Как работает бот

1. Пользователь шлёт номер рейса (`SU2128`) → бот пробует его на настроенных
   табло в обоих направлениях (`registry.probe`), добирает даты, которых на
   табло ещё нет, из расписания AeroDataBox (`registry.search`) и показывает
   кнопками даты на сегодня и 5 дней вперёд. Без `AERODATABOX_API_KEY` — только
   даты с табло.
2. Тап по дате → подписка в SQLite + карточка текущего статуса. Для даты из
   расписания — «По расписанию» (план из кэша поиска, без нового запроса) и
   пометка, что изменения пойдут, когда рейс появится на табло. Рейс в наш
   аэропорт (DXB→DME) ведётся по табло прилёта и дате прилёта, как у табло.
3. Поллер снимает снапшот каждой активной подписки, считает
   `diff_snapshots(prev, curr)` и шлёт **только изменения**, по хронологии: регистрация открыта/закрыта → посадка → вылет → прилёт, плюс
   выход, терминал, лента багажа, отмена. Сдвиг времени — от 5 минут: табло
   дёргает оценку на минуту-две, мелкий сдвиг пугать незачем.
4. Частота опроса адаптивная: раз в час, пока до вылета >6 ч; раз в
   `POLL_INTERVAL_SEC` (5 мин) в окне у вылета и в воздухе; раз в 2 мин с
   начала посадки.
5. Рейс, которого ещё нет на табло (дата дальше завтра), до 00:00 МСК
   накануне даты не опрашивается — табло и AirLabs его всё равно не покажут.
6. Подписка снимается сама: после прилёта, при отмене и через сутки после
   даты рейса — в последнем случае с пушем «▸ Перестал следить за …» и причиной
   (не появился на табло / прилёта табло не показало).
7. Если табло упали или не ответили за 15 с, бот так и говорит: «табло dme.ru
   сейчас не отвечают — попробуйте через несколько минут», а при частичном
   сбое показывает найденные даты с пометкой. Пока идёт поиск, в чате
   «печатает»; после тапа по дате кнопка сразу гаснет, карточка приходит
   следом. Провал транспорта табло (напрямую / RU-прокси) помнится 5 минут,
   потом ступень пробуется снова.

## Бот в группе и доступ

- Подписка живёт в том чате, где её оформили: подписались в группе — пуши
  идут в группу. В группе с темами (форум) — в ту тему, где подписались;
  подписка на тот же рейс из другой темы переносит пуши туда. Тему удалили —
  бот забывает её, и дальше пуши идут в General.
- Бота удалили из группы (заблокировали в личке) или чата больше нет — при
  первом же пуше бот снимает все подписки этого чата. Группа стала
  супергруппой (у неё меняется chat_id) — подписки переезжают на новый
  chat_id при первом пуше, сам пуш уходит уже туда.
- В группе у Telegram включён режим приватности: бот видит только команды.
  Поэтому номер там шлют командой `/track EK770` (в личке можно и просто
  `EK770`). Голый номер в группе бот не обрабатывает, даже если видит всё
  (бот-админ): «10 30» тоже похоже на рейс, а поиск платный.
- `OWNER_IDS` в `.env` — Telegram user id через запятую (узнать: @userinfobot):
  кто управляет ботом **в группах**; сообщения и кнопки остальных в группе бот
  молча игнорирует. Личка открыта всем. Пусто — в группах тоже всем.
  Писать боту в группе нужно от своего имени: анонимный админ для Telegram —
  другой пользователь (GroupAnonymousBot), его команды бот не примет.
- `GREET_NAMES` в `.env` — `username=Имя Отчество` через запятую: на `/start`
  бот здоровается с ними по имени и на «вы». Имена — только в `.env`
  (репозиторий публичный).
- Как добавить: @BotFather → `/mybots` → бот → Bot Settings → **Allow Groups**
  включить (Group Privacy оставить включённым) → добавить бота в группу →
  `/track <номер>` и выбрать дату.

Диффер считает по структурным полям (появление факта), а не по сырому тексту
статуса табло — тот шумный. Текстовые события — отмена и, для табло без времён
фаз (VKO, DME), смена статуса без цифр («Регистрация закрыта», «Идёт посадка»):
она шлётся, если событие хронологии в том же опросе не сказало того же; смена
выхода или терминала её не глушит.

Кроме фактов фаз, пуш приходит, когда: назначили или сменили стойки регистрации
(до её начала; DME показывает стойки за часы), перенесли план начала регистрации
или посадки от 5 мин (посадку — только без задержки вылета, о ней свой пуш),
заменили самолёт, сменилась зона вылета/прилёта. Не шлём: сдвиг меньше 5 мин,
сырой статус с цифрами, пропадание выхода из бегущей строки DME, сравнение плиток
из разных источников (табло не ответило, ответил резервный AirLabs).

## Формат сообщений

Время — местное для аэропорта; если аэропорт не в поясе МСК, рядом в скобках
МСК: «🕒 Вылет 09:10 (08:10 МСК) · Прилёт 16:40 (17:40 МСК)», в пушах так же.

Карточка при подписке (значки — кастомные эмодзи пака, здесь их запасные эмодзи):

```
GF013 · Gulf Air · Airbus A321neo
📅 6 сентября
✈️ SVO Москва → BAH Бахрейн       ← конечная точка, не ближайшая посадка
🗺️ через TBS Тбилиси              ← только у рейсов с промежуточной посадкой
🕒 Вылет 10:45 · Прилёт 19:35     ← при сдвиге: ~~10:45~~ 11:30

⚪ Регистрация в 07:45            ← точка статуса: задержка, регистрация, в воздухе, прилетел, отменён
⌛ До регистрации 12 ч 50 мин     ← обратный отсчёт

🛎️ Стойки — · откроется в 07:45
🚪 Выход 146 · посадка за 40 мин до вылета
🏢 Терминал C

Хронология
⚪ Регистрация · 07:45            ← ✅ — уже было, ⚪ — ещё ждём
⚪ Регистрация закрыта · 09:45
⚪ Посадка · ждём табло
⚪ Вылет · 10:45
⚪ Прилёт · 19:35
```

Значки — одноцветный пак кастомных эмодзи [FlightStatusMinimal](https://t.me/addemoji/FlightStatusMinimal)
(Phosphor Icons, перекрашивается под цвет текста). Ключи значков и запасные эмодзи —
`flight_bot/icons.py`; id берутся при старте из `getStickerSet` по порядку значков
в паке, в репозитории их нет. Имя пака — `EMOJI_SET` в `.env` (по умолчанию
`FlightStatusMinimal`, пусто — без пака). Слать кастомные эмодзи бот может, только
если у владельца бота Telegram Premium (Bot API 9.4). Пак не загрузился (нет сети,
в паке другое число значков) — в пушах обычные запасные эмодзи, в логе warning.
Значок с тегом `<tg-emoji>` несёт внутри запасное эмодзи: его покажут уведомления.
Для прилёта — свои плитки (лента багажа, гейт прилёта) и два шага. Пуш — только
дельта: заголовок и строки изменений, по-человечески и на «ты»:

```
🔔 EK770 · Дубай → Кейптаун · 16 октября
🕒 Вылет позже на 30 мин: теперь 09:40 (08:40 МСК), было 09:10
🚪 Новый выход на посадку в DXB: A17 (был B24)
```

Смена выхода называет аэропорт и вид выхода (на посадку или гейт прилёта).
Если прошлый и новый снимки из разных источников (табло не ответило, ответил
резервный), смену выхода не шлём: значения разных источников несравнимы.
В кнопках дат прошедшие дни не предлагаются.

## Разработка

```bash
pip install -r requirements.txt pytest ruff
ruff check . && pytest
```

CI — GitHub Actions (`.github/workflows/tests.yml`): `ruff check` и pytest на Python 3.12
на каждый пуш и PR; для публичного репозитория бесплатно. Пуш в `main`
после зелёных тестов выкатывается на сервер (см. «Деплой»). Зависимости в
`requirements.txt` зафиксированы точно — обновлять осознанно. При мерже в `main`
раздел `Unreleased` в `CHANGELOG.md` получает дату: что ниже даты — то на проде.

Тесты не ходят в сеть: парсер SVO гоняется на боевой фикстуре, поллер — с
подменённым источником.

## Деплой

Сервер бота, каталог `/opt/flight-bot` — отдельно от сайта,
доставка через `git push`/`git pull`. Секреты — в `/opt/flight-bot/.env`
(см. `.env.example`, в git не коммитится).

```bash
cd /opt/flight-bot && git pull
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
sudo cp deploy/flight-bot.service /etc/systemd/system/
sudo systemctl daemon-reload && sudo systemctl enable --now flight-bot
```

Обновление — автоматически: пуш в `main` с зелёными тестами выкатывает job `deploy`
(`.github/workflows/tests.yml`) по SSH через `deploy/deploy.sh`: fast-forward на этот
коммит, `pip install` при смене `requirements.txt`, рестарт, 30 с проверки, что сервис
не перезапускается; не держится — откат на прежний коммит (ADR-0005). Установка ключа и
sudoers — в заголовке `deploy/deploy.sh`. Секреты репозитория (environment `production`):
`DEPLOY_SSH_KEY`, `DEPLOY_KNOWN_HOSTS` (`ssh-keyscan -p <порт> <хост>`), `DEPLOY_TARGET`
(`vbondarev@<хост>`), `DEPLOY_PORT` (пусто — 22). Вручную — как раньше:
`git pull && sudo systemctl restart flight-bot`. Юниты в `deploy/` выкатка не
переустанавливает: после их изменения — `sudo cp … /etc/systemd/system/ &&
sudo systemctl daemon-reload && sudo systemctl restart flight-bot`. В юните
`WatchdogSec=300`: поллер раз в минуту шлёт `WATCHDOG=1`, зависший процесс
systemd перезапустит.

Копия базы — каждый день в 04:00 МСК в `~/flight-bot-backup/daily`, 14 дней
(`deploy/flight-bot-backup.timer`, инструкция в заголовке юнита). Вручную:
`.venv/bin/python -m flight_bot.backup`. `BACKUP_RSYNC_TARGET` в `.env`
(`user@host:путь/`) — после копии каталог зеркалится на другой хост `rsync`-ом.

Транспорт для табло с гео-блоком и для табло «только для браузера» —
`deploy/ru-proxy.service` (SSH-туннель до RU-хоста: SOCKS + проброс порта
рендер-сервиса) и `deploy/render` (Docker на RU-хосте). AeroDataBox
(RapidAPI) отвечает 451 сети сервера бота — его запросы идут через
`deploy/dk-proxy.service` (SOCKS до DK-хоста, `SCHEDULE_PROXY_URL`). Инструкции — в
заголовках этих файлов.
